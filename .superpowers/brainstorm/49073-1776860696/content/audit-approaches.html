改善方案对比

针对三大问题（Timeline 过载、颜色混乱、硬编码泛滥）的三种解决策略

方案 A：渐进式手术（推荐）

精准打击，按影响排序 推荐

执行步骤

  1. Timeline 拆分 — 拆成 4 个子页面（浏览/创建/任务/成长）
  2. 灰色统一 — 全局替换 3 套灰色 → 设计系统暖灰
  3. 品牌渐变统一 — 全局替换 → token 定义的 #FFA065→#FF7A3E
  4. 高频文件迁移 — Top 5 硬编码文件逐步改为 token

评估

工期：3-4 个工作日
回归风险：低 — 每步独立可验证
覆盖率：解决 80% 视觉不一致
测试策略：每步完成后截图对比
核心原则：不动已经拿到 A/A+ 的页面（Auth、Dashboard、AIChat），只修复 C+ 和 B 级别页面，再统一全局色值。

方案 B：设计系统优先

执行步骤

  1. 扩建 token 系统 — 新增 semantic tokens（如 --color-bg-timeline）
  2. 创建 eslint 规则 — 禁止新代码使用硬编码色值
  3. 批量替换脚本 — 自动映射 1245 个硬编码 → token
  4. Timeline 拆分 — 同方案 A

评估

工期：5-6 个工作日
回归风险：中 — 脚本批量替换可能引入细微差异
覆盖率：解决 95% 不一致，从根源预防
测试策略：全页面截图回归 + 人工 review
优势：一劳永逸，未来新增页面/组件自动合规。代价：工期多 50%，需要更多测试。

方案 C：仅修复 Timeline

执行步骤

  1. Timeline 拆分 — 同方案 A 第一步
  2. 迁移 Timeline 内硬编码 — 仅 194 个色值
  3. 不触碰其他页面

评估

工期：1-2 个工作日
回归风险：极低 — 只动一个模块
覆盖率：解决最差页面，其余保持现状
测试策略：Timeline 模块截图对比
适合：时间紧迫时先救最严重的，后续再跟进全局统一。
