# 意图识别系统改造（V2 关键词规则 → V3 LLM Function Calling）

> 把意图识别从"字符串规则匹配"演进到"LLM 工具调用"的完整工程记录，准确率从 ~70% 提升到 100%。

**日期**：2026-06-21 ~ 2026-06-22
**所涉版本**：Agent v3.1
**主要文件**：[AgentRouter.ts](../../backend/src/agent/core/AgentRouter.ts) / [AgentLoop.ts](../../backend/src/agent/core/AgentLoop.ts) / [systemPrompt.ts](../../backend/src/agent/prompts/systemPrompt.ts) / [featureFlags.ts](../../backend/src/config/featureFlags.ts)

## 一、起点：我们为什么要改

### 1.1 原始症状

测试中反复观察到以下错判：

| 用户消息 | 期望意图 | 实际意图 | 错因 |
| --- | --- | --- | --- |
| "下次该打什么疫苗" | check_vaccine | ADD_vaccine_record | 命中"疫苗"关键词但忽略"下次"上下文 |
| "我家猫今天 8 斤" | ADD_weight_record | general_knowledge | 词表里没有"斤"和"体重"组合 |
| "妙三多疫苗" | ADD_vaccine_record | ADD_growth_record | "妙三多"不在词表 |
| "猫最近精神不好" | check_health | general_knowledge | "精神不好"不是健康关键词 |

### 1.2 用户反馈触发讨论

**用户**："现在有一个问题需要确认，意图的识别是通过关键词来实现的吗？"

**问题暴露**：整个意图分类是 14 个意图 × 200+ 关键词的字典匹配。每加一个表达就要扩词表，词表越大越脆弱。

### 1.3 进一步暴露的更深层问题：置信度是"伪置信度"

**用户**："方案 C 是有问题的，因为置信度的计算本身就有问题"

#### 调研后确认的事实

[AgentRouter.ts](../../backend/src/agent/core/AgentRouter.ts#L84-L97) 中的 `confidence` 计算逻辑：

```typescript
function matchDensity(message: string, patterns: string[]): number {
  const matches = patterns.filter((p) => message.toLowerCase().includes(p.toLowerCase()))
  const matchChars = matches.reduce((sum, p) => sum + p.length, 0)
  return Math.min(matchChars / message.length, 1)
}
// confidence = 0.6 + density × 0.35   // 单领域
// confidence = 0.9                    // 写工具硬编码
```

**这个数字只反映"关键词占消息字符数的比例"，不反映任何概率含义**。三个反直觉案例：

| 用户输入 | matchDensity | confidence | 真实可靠性 |
| --- | --- | --- | --- |
| "体重"（2 字） | 100% | 0.95 | ❌ 不知道用户想录入还是查询 |
| "我家猫精神不好，体重轻了"（20 字） | 4/20 = 20% | 0.91 | ❌ 实质是健康咨询，被强判为体重录入 |
| 不同意图的 0.9 互相比较 | - | - | ❌ 硬编码值无统一度量基准 |

**结论**：基于伪置信度做"if confidence > 0.85 走规则，否则走 LLM"的混合方案不成立。

## 二、调研：主流意图分类方案

完整调研报告：[意图分类调研报告.html](../意图分类调研报告.html)

### 2.1 八大方案对比

| 方案 | 准确率 | 延迟 | 数据需求 | 置信度 | 评级 |
| --- | --- | --- | --- | --- | --- |
| 规则关键词 | ⚠️ 已知 98% / 自然语言 55% | <1ms | 0 | ❌ 字符占比 | 2017 范式 |
| SVM / LR | 72~86% | ~5ms | 30~200/类 | 🟡 | 2020 前 |
| Rasa DIET | 87~92% | ~10ms | 50~300/类 | 🟢 | 工业次选 |
| BERT 微调 | 93~95% | ~50ms | 100~500/类 | 🟢 | 大厂方案 |
| Sentence Embedding | 89~91% | ~60ms | 5~20/类 | 🟢 cos_sim 真实 | **现代主流** |
| LLM Few-shot | 88~91% | ~1000ms | few-shot | 🔴 自报不准 | 简单场景 |
| LLM Function Calling | 93~96% | ~800ms | tool description | 🟢 触发信号 | **意图≈工具天然适配** |
| Hybrid Routing | 95~97% | ~120ms | 多策略 | 🟢🟢 | **2024~2025 SOTA** |

### 2.2 关键洞察

1. **项目已具备 LLM Tool-Calling 能力但被关闭** — [AgentLoop.ts](../../backend/src/agent/core/AgentLoop.ts) 完整实现了 ReAct 循环，只是被 `isV2ToolIntent` 关键词正则强制降级
2. **意图与工具一一对应** — PangHu 14 个意图与 14 个工具天然 1:1 映射，这正是 Function Calling 的最佳场景
3. **写入安全机制已就绪** — `confirmationToken` 二次确认能兜底 LLM 误判
4. **基础设施 100% 齐备** — Zhipu LLM Client / Embedding / Confirmation 都已就位

### 2.3 选定方案

- **短期 Step 1**：开放 LLM Function Calling（本次改造）
- **中期 Step 2**：补 Embedding 召回层（待后续）
- **长期 Step 3**：评估闭环（待后续）

                              语义理解

### 3.2 改动清单（7 个核心改动）

#### ① AgentLoop 支持 write 工具确认机制

[AgentLoop.ts](../../backend/src/agent/core/AgentLoop.ts) 新增 `onPendingConfirmation` 回调：

```typescript
export interface AgentLoopRunInput {
  // ...
  /** 写工具被 LLM 选中且未确认时回调，返回 true 表示已外部接管（中断 loop） */
  onPendingConfirmation?: (pending: PendingConfirmation) => boolean | void
}
```

执行前扫描 LLM 选中的工具，若是 write 且无 confirmationToken，立即中断 loop 并推送 `pending_confirmation` 事件给前端：

```typescript
const writePending = callsInOrder.find((c) => {
  const t = this.toolMap.get(c.name)
  return t?.permissions?.includes('write') && !ctx.confirmationToken?.verified
})
if (writePending) {
  onPendingConfirmation?.({ toolName: writePending.name, parameters: parseArgs(writePending.args) })
  break  // 中断 loop
}
```

#### ② CatAgent.handleStreaming 让 LLM 路由主导

[agent/index.ts](../../backend/src/agent/index.ts) **完全移除** `isV2ToolIntent` 关键词降级：

```typescript
// 之前：命中关键词 → 强制走 V2 旧链路
if (useNewLoop && !this.isV2ToolIntent(userMessage) && attachments.length === 0) { /* ... */ }

// 现在：只有图片附件保留 V2 fast-path（LLM 看不到图片）
if (useNewLoop && attachments.length === 0) {
  return this.handleStreamingViaLoop(/* ... */)
}
```

#### ③ 全部 14 个工具纳入 AgentLoop

```typescript
// 之前：只暴露 5 个 readonly 工具
private readonly agentLoop = new AgentLoop(zhipuaiClient, this.getReadOnlyTools(), /* ... */)

// 现在：全部 14 个（含 write）
private readonly agentLoop = new AgentLoop(zhipuaiClient, listTools(), /* ... */)
```

#### ④ Feature Flag 全量开放 ⭐ 最关键的隐性修复

[featureFlags.ts](../../backend/src/config/featureFlags.ts) 中 `LLM_TOOL_CALLING_LOOP` 之前是：

```typescript
rollout: {
  environment: { production: false },
  userSegment: 'internal',   // ⚠️ 这一行让所有非内部用户绕开 V3 路由
  percentage: 100,
}
```

**这是一个隐藏极深的 bug**：测试用户默认 segment = 'all'，永远不满足 'internal'，导致**所有测试一直跑在 V2 旧链路上**。修复为：

```typescript
rollout: {
  environment: { production: true },
  userSegment: 'all',
  percentage: 100,
}
```

#### ⑤ 模型升级：glm-4-flash → glm-4.5-flash

通过 API 探测确定可用的最强免费模型。所有引用替换为 `glm-4.5-flash`：

| 文件 | 改动 |
| --- | --- |
| [zhipuaiClient.ts](../../backend/src/agent/llm/zhipuaiClient.ts#L8) | DEFAULT_MODEL |
| [ai.service.ts](../../backend/src/services/ai.service.ts#L14) | DEFAULT_MODEL |
| [prompt-eval.ts](../../backend/src/eval/prompt-eval.ts#L126) | 评估脚本默认模型 |
| [.env.example](../../backend/.env.example#L11) | 环境变量示例 |

同时为思考型模型增加 `thinking: { type: 'disabled' }` 关闭思考（工具调用不需要）：

```typescript
const body = {
  model,
  messages: opts.messages,
  // glm-4.5/4.6 系列默认开启思考模式会大幅增加延迟，工具调用场景关闭它
  thinking: { type: 'disabled' },
}
```

#### ⑥ 写入工具 description 全面重写

每个 write 工具的 description 改成"何时调用 / 何时不要调用 / 数据要求 / 写入提示"四段结构：

```typescript
// ADD_vaccine_record
description:
  '为猫咪登记一条疫苗接种或驱虫记录，写入健康档案并自动计算下次到期时间。\n' +
  '【何时调用】用户陈述"刚完成/已经完成/今天打/已经做了"接种或驱虫\n' +
  '【严禁调用】用户询问"下次什么时候打/疫苗到期没/该打什么疫苗了"\n' +
  '判断要点：含"下次/什么时候/到期"等未来时间副词的属于查询；\n' +
  '       含"今天/刚才/已经"等过去时副词的才是录入。\n' +
  '【写入操作】需要用户在弹出的卡片上点击确认后才会真正保存。',
```

#### ⑦ systemPrompt 加入 Few-shot 示例 ⭐ 最有效的优化

[systemPrompt.ts](../../backend/src/agent/prompts/systemPrompt.ts) 新增 24 个对照范例，覆盖 6 个意图分组：

## 五、关键经验与教训

### 5.1 What Worked（有效的工程决策）

1. **先做调研再动手** — [意图分类调研报告.html](../意图分类调研报告.html) 让我们避免了在伪置信度上修修补补，直接定位到 Function Calling 这条路。
2. **保留写入二次确认机制** — LLM 路由错了也不会误写库，大幅降低改造风险。
3. **图片附件保留 V2 fast-path** — LLM 看不到图片，硬规则反而是最稳的方案。
4. **Feature Flag 配合灰度** — 改 flag 即可一键回滚，无需代码 revert。
5. **Few-shot 示例性价比最高** — 24 个范例对照让准确率从 78% → 100%，仅加 600 tokens。

### 5.2 What Hurt（踩到的坑）

1. **Feature Flag userSegment 没有暴露日志** — 测试一直跑 V2 旧链路而不自知，浪费了几轮调试时间。
   - **教训**：flag 路由必须打日志，标明每次请求实际走的链路。
2. **模型名探测靠 trial-and-error** — `glm-4.7-flash` 公告说免费但实际 500，只能逐个试。
   - **教训**：接入新模型前应先用最小 curl 探测，不要依赖文档。
3. **思考模式默认开启** — glm-4.5-flash 默认开启 thinking 导致大量 tokens 浪费在内部推理上。
   - **教训**：思考模型用于工具调用时必须显式 `thinking: { type: 'disabled' }`。
4. **Description 改进单独效果有限** — 只改 tool description 不加 Few-shot，准确率没有显著提升。
   - **教训**：Description 提供"是什么"，Few-shot 提供"怎么用"，两者缺一不可。
5. **失败 case 表面上看像模型问题，实际是工程问题** — 之前以为"glm-4-flash 能力不足"，其实是 feature flag 没生效。
   - **教训**：模型不背锅前先验证全链路。

### 5.3 五个反复出现的踩坑模式

| 模式 | 表现 | 解法 |
| --- | --- | --- |
| 配置静默失败 | flag 默认值与生产期望不符 | 启动日志打印关键配置 |
| 模型版本错位 | API 文档与实际可用模型有差异 | 接入前 curl 探测 |
| 思考模式溢出 | tokens 全花在推理上 | 显式禁用 thinking |
| 提示词与示例脱节 | 只写规则不给案例 | Few-shot 必须配套 |
| 测试用例覆盖偏窄 | 只测高频路径 | 包含"易混淆边界" |

## 七、后续演进方向

### 7.1 Step 2：Embedding 召回层（下一步）

利用 [knowledge.service.ts](../../backend/src/services/knowledge.service.ts) 已有的 embedding 能力，做意图 anchor 句相似度匹配：

```text
用户消息 → embedding → 余弦相似度 top-1
       ↓
     ≥ 0.85 → 直接返回意图（<100ms，跳过 LLM）
     < 0.85 → 走 LLM 路由（~800ms）
```

预期 60% 流量可走 Embedding 快速通道，平均延迟降到 ~200ms。

### 7.2 Step 3：评估闭环

- 收集真实用户消息 + 标注 → 评测集
- 监控 LLM 路由 confusion matrix
- 周/月对比准确率，定位漂移
- 用户在 RecordConfirmCard 上的"取消"行为 → 标记为可能的意图误判

### 7.3 不做的事

- ❌ 不引入 BERT 微调 — 14 类意图规模不需要，且部署复杂度过高
- ❌ 不依赖 LLM 自报的 confidence 数字 — 校准度差，不可信
- ❌ 不重写 V2 关键词路由 — V2 已废弃，后续可直接删除
